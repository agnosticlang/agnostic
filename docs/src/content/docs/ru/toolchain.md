## Флаги командной строки

```
agnostic <source.agn> [options]
  --backend=llvm|gcc       выбор бэкенда кодогенерации (по умолчанию: llvm)
  --mem=arc|manual|orc     выбор режима управления памятью (по умолчанию: arc)
  --target-os=linux|freebsd|windows|hurd  (по умолчанию: linux)
  --output=<path>          путь к выходному исполняемому файлу
  --version                вывести версию и выйти
  --help                   вывести справку и выйти
```

`--llvm` и `--gcc` принимаются как сокращения для соответствующего значения `--backend=`.

## Бэкенды

### llvm (по умолчанию)

Генерирует нативный машинный код через C++ API LLVM (`IRBuilder`, `Module`, `TargetMachine`), затем линкует его в статический исполняемый файл командой `cc -nostdlib -static -no-pie -e _start`. Результат не линкуется с libc; стандартная библиотека и рантайм обращаются к ядру Linux через сырые системные вызовы (`src/platform/linux`).

### gcc

Генерирует нативный машинный код через libgccjit, встраиваемую библиотеку кодогенерации GCC, и линкует так же, как бэкенд `llvm`. Обладает тем же набором возможностей, что и `llvm` (замыкания, структуры, указатели, `comptime`, все три режима `--mem=`), и использует те же статические библиотеки рантайма и линковку без libc. Для сборки компилятора с этим бэкендом нужны `libgccjit.h` и `libgccjit.so` в системе (Arch Linux: пакет `libgccjit`; Fedora: `libgccjit-devel`; Debian/Ubuntu: `libgccjit-dev`).

## Режимы памяти

- **arc** (по умолчанию): подсчёт ссылок. `agn_rt_retain`/`agn_rt_release` вызываются вокруг присваиваний, ссылающихся на уже существующее значение; свежая конструкция (литерал, результат вызова, литерал структуры) повторно не удерживается, потому что уже владеет своей единственной ссылкой.
- **manual**: только `agn_rt_alloc`. Ничего не освобождается автоматически.
- **orc**: региональное выделение. Вызов функции открывает регион при входе и разом освобождает всё, выделенное в нём, на любом пути выхода, включая `main`. Функция открывает собственный регион, только если ничто из выделенного ею не может пережить вызов. Компилятор решает это по типам: тип возврата не содержит `string`, указателя или функции, ни напрямую, ни в структуре или массиве; ни один параметр не является функцией или указателем на такой тип (получатель метода считается указателем на свою структуру); у замыкания ни одна захваченная переменная не содержит таких значений. Любая другая функция выделяет память в регионе ближайшего вызывающего, у которого есть собственный, поэтому возвращённые строки и замыкания, а также значения, записанные через указатели или в захваченные переменные, остаются корректными. Такие значения живут до возврата из этого вызывающего: цикл в `main`, который вызывает функцию, возвращающую новую строку, хранит все эти строки до выхода из `main`.

## target-os

Реальная реализация платформы есть у всех четырёх целей. Бэкенд `freebsd` линкует сырые amd64-сисколлы напрямую (без libc) и помечает итоговый статический ELF как бинарник FreeBSD с помощью ELF-заметки ABI FreeBSD (`.note.tag`, `NT_FREEBSD_ABI_TAG`, версия ОС 14.0), той же, что добавляют стартовые файлы самой FreeBSD. Заметка приходит из стартового кода FreeBSD, поэтому работает с любым линкером и с обоими бэкендами. Проверено реальным запуском скомпилированных бинарников с обоих бэкендов, `llvm` и `gcc` (включая замыкания и структуры, которые задействуют аллокатор кучи), на настоящей VM с FreeBSD 15.1.

Цель `windows` выдаёт консольный исполняемый файл PE32+, `<output>.exe`, для x86-64 так же, как это делает Go: программа обращается напрямую к kernel32.dll, без C-рантайма, без библиотек MSVC или MinGW и без сырых системных вызовов NT, номера которых меняются от сборки к сборке Windows. Рантайм импортирует фиксированный список функций kernel32 (`src/platform/windows/kernel32.def`), а сборка компилятора превращает этот список в import-библиотеку с помощью `llvm-dlltool`. Аргументы командной строки берутся из `GetCommandLineW`, разбираются по стандартным правилам кавычек Windows и передаются программе в UTF-8. Цели нужен `--backend=llvm`, поскольку libgccjit генерирует код только для хоста, и `lld-link` в `PATH` для линковки. Проверено запуском тестовых программ под Wine.

Цель `hurd` выдаёт статический исполняемый ELF для x86-64 GNU/Hurd без glibc. Программа обращается к GNU Mach и серверам Hurd напрямую: Mach-ловушки для `mach_msg`, `vm_allocate`, `vm_deallocate`, `mach_port_deallocate` и `task_terminate`, а также MIG-сообщения, которые рантайм кодирует сам, для `exec_startup_get_info` (аргументы, файловые дескрипторы и начальные порты), `io_read`, `io_write`, `dir_lookup`, `file_set_size` и `proc_mark_exit`. Поиск имён файлов выполняет повторы, которые запрашивает сервер, включая абсолютные символические ссылки; поиск, требующий переаутентификации или другого магического имени, завершается ошибкой. Программа не регистрирует порт сообщений и поэтому не получает сигналы. На живой системе Hurd эта цель ещё не запускалась: раскладка сообщений взята из исходников GNU Mach, MIG и Hurd, а тесты проверяют только компиляцию и линковку.

## Диагностика

Ошибки типов сообщают настоящие `файл:строка:колонка`, подсвеченный указатель на строку исходника и, если компилятор находит достаточно близкое совпадение, — подсказку:

```
error: variable 'countr' not declared (did you mean 'counter'?) (in main)
  --> hello.agn:6:5
```

Подсказки основаны на расстоянии Левенштейна и появляются только при наличии достаточно близкого варианта: для необъявленных переменных (среди локальных переменных и функций верхнего уровня в области видимости), для неизвестных полей структуры и неизвестных имён структур. Для `object.member(...)` компилятор сначала проверяет, известен ли сам `object` — модуль, переменная типа структуры или импорт (`stdi.Println` подскажет `stdio`); если `object` разрешился, а `member` — нет, подсказка ищется среди членов именно этой структуры или модуля, включая поля структуры, хранящие значение-функцию, наравне с настоящими методами (`p.writ(...)` подскажет поле `write`).

## Сборка компилятора из исходников

```sh
cmake -S . -B build
cmake --build build -j$(nproc)
```

Нужны файлы разработки LLVM в путях поиска CMake и компилятор с поддержкой C++20. См. [Начало работы](/ru/getting-started/). Для цели `windows` при сборке также нужны `clang`, `llvm-lib` и `llvm-dlltool`; если чего-то не хватает, CMake отключает цель и сообщает об этом.

Сборка раскручивает себя сама. Сначала линкуется `agnostic_stage0`, компилятор с лексером на C++ из `old/lexer`, затем он компилирует самостоятельный лексер `src/lexer/lexer.agn`, и итоговый `agnostic` линкуется уже с ним. `-DAGNOSTIC_BOOTSTRAP_COMPILER=<путь>` компилирует `lexer.agn` уже имеющимся компилятором вместо сборки stage 0. `-DAGNOSTIC_BOOTSTRAP=ON` собирает только компилятор с лексером на C++, под именем `agnostic`.

## Установка из пакета

CI собирает `.deb`, `.rpm`, пакет Arch и `.apk` для Alpine при каждом push тега и прикрепляет их к релизу на GitHub. Все четыре ставят одну и ту же раскладку: бинарник `agnostic` в `bin/`, статические библиотеки рантайма в `lib/agnostic/`, файлы `.agn` стандартной библиотеки в `share/agnostic/stdlib/`. Компилятор сначала ищет свою стандартную библиотеку и библиотеки рантайма относительно собственного пути, а если не находит — переходит к раскладке, используемой при запуске прямо из директории сборки, так что и установленный пакет, и локально собранный бинарник работают без дополнительной настройки.
