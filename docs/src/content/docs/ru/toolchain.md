## Флаги командной строки

```
agnostic <source.agn> [options]
  --backend=llvm|nvm|gcc   выбор бэкенда кодогенерации (по умолчанию: llvm)
  --mem=arc|manual|orc     выбор режима управления памятью (по умолчанию: arc)
  --target-os=linux|freebsd|windows|hurd  (по умолчанию: linux, реализован только linux)
  --output=<path>          путь к выходному исполняемому файлу
  --version                вывести версию и выйти
  --help                   вывести справку и выйти
```

`--llvm`, `--nvm` и `--gcc` принимаются как сокращения для соответствующего значения `--backend=`.

## Бэкенды

### llvm (по умолчанию)

Генерирует нативный машинный код через C++ API LLVM (`IRBuilder`, `Module`, `TargetMachine`), затем линкует его в статический исполняемый файл командой `cc -nostdlib -static -no-pie -e _start`. Результат не линкуется с libc; стандартная библиотека и рантайм обращаются к ядру Linux через сырые системные вызовы (`src/platform/linux`).

### nvm

Генерирует байткод для Novaria Virtual Machine и записывает его в `<output>.bin`. Для запуска нужно ядро Novaria или отдельный интерпретатор байткода; в этом репозитории их нет. Не поддерживаются под этим бэкендом: замыкания и значения-функции, `&` (взятие адреса), интерполяция шаблонных строк, строковый оператор `++`, а также `stdio.ReadInt`/`ReadChar`/`ReadLine` (у stdin в ядре Novaria нет рабочего пути чтения). Каждый такой случай — ошибка компиляции, называющая конкретную конструкцию, а не тихая неверная генерация кода.

### gcc

Генерирует нативный машинный код через libgccjit, встраиваемую библиотеку кодогенерации GCC, и линкует так же, как бэкенд `llvm`. Обладает тем же набором возможностей, что и `llvm` (замыкания, структуры, указатели, `comptime`, все три режима `--mem=`), и использует те же статические библиотеки рантайма и линковку без libc. Для сборки компилятора с этим бэкендом нужны `libgccjit.h` и `libgccjit.so` в системе (Arch Linux: пакет `libgccjit`; Fedora: `libgccjit-devel`; Debian/Ubuntu: `libgccjit-dev`).

## Режимы памяти

`--mem=` влияет только на бэкенд `llvm`; у байткода `nvm` нет рантайма выделения кучи, для которого выбирать стратегию.

- **arc** (по умолчанию): подсчёт ссылок. `agn_rt_retain`/`agn_rt_release` вызываются вокруг присваиваний, ссылающихся на уже существующее значение; свежая конструкция (литерал, результат вызова, литерал структуры) повторно не удерживается, потому что уже владеет своей единственной ссылкой.
- **manual**: только `agn_rt_alloc`. Ничего не освобождается автоматически.
- **orc**: региональное выделение. Каждый вызов функции открывает регион при входе и разом освобождает всё, выделенное в нём, на любом пути выхода, включая `main`. Это дешевле, чем `arc`, но с реальным ограничением: указатель, выделенный внутри функции и возвращённый (или сохранённый где-то, откуда до него можно дотянуться) вызывающей стороне, небезопасен после того, как регион этой функции разрушен. Анализа «убегающих» указателей нет; ответственность за это лежит на вызывающей стороне.

## target-os

Реальная реализация платформы есть только для `linux`. `freebsd`, `windows` и `hurd` — нереализованные заглушки; компиляция с `--backend=llvm` и любым `--target-os=`, кроме `linux`, завершается ошибкой «only --target-os=linux has a real platform/runtime implementation».

## Диагностика

Ошибки типов сообщают настоящие `файл:строка:колонка`, подсвеченный указатель на строку исходника и, если компилятор находит достаточно близкое совпадение, — подсказку:

```
error: variable 'countr' not declared (did you mean 'counter'?) (in main)
  --> hello.agn:6:5
```

Подсказки основаны на расстоянии Левенштейна и появляются только при наличии достаточно близкого варианта: для необъявленных переменных (среди локальных переменных и функций верхнего уровня в области видимости), для неизвестных полей структуры и неизвестных имён структур. Для `object.member(...)` компилятор сначала проверяет, известен ли сам `object` — модуль, переменная типа структуры или импорт (`stdi.Println` подскажет `stdio`); если `object` разрешился, а `member` — нет, подсказка ищется среди членов именно этой структуры или модуля, включая поля структуры, хранящие значение-функцию, наравне с настоящими методами (`p.writ(...)` подскажет поле `write`).

## Сборка компилятора из исходников

```sh
cmake -S . -B build
cmake --build build -j$(nproc)
```

Нужны файлы разработки LLVM в путях поиска CMake и компилятор с поддержкой C++20. См. [Начало работы](/ru/getting-started/).

## Установка из пакета

CI собирает `.deb`, `.rpm`, пакет Arch и `.apk` для Alpine при каждом push тега и прикрепляет их к релизу на GitHub. Все четыре ставят одну и ту же раскладку: бинарник `agnostic` в `bin/`, статические библиотеки рантайма в `lib/agnostic/`, файлы `.agn` стандартной библиотеки в `share/agnostic/stdlib/`. Компилятор сначала ищет свою стандартную библиотеку и библиотеки рантайма относительно собственного пути, а если не находит — переходит к раскладке, используемой при запуске прямо из директории сборки, так что и установленный пакет, и локально собранный бинарник работают без дополнительной настройки.
